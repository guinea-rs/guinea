# Фичи, состояние и то, что доходит до UI

**Статус: сделано.** Заменило нынешнюю форму `contracts.rs` (пять объявлений
на фичу), четыре способа заявить владение редьюсером в `FeatureInitContext` и
машинерию групп с `InGroup`.

Два из трёх пунктов «Открытого» в конце закрылись сами: `Reducer::DrivenBy` не
понадобился — актор ушёл из API целиком, и скоуп ключуется действием; порядок
сноса развернулся, как только зависимости стали объявленными. Третий —
обязательство `Exports` — закрыт сверкой с тем, что реально заявлено, потому
что возвращаемым значением он быть не может: его читает `Reaches` на этапе
компиляции.

Дополняет [routing.md](routing.md): там дерево маршрутов, гварды, адресуемость
и типизированные параметры.

## Слои

| слой | знает | не знает |
|---|---|---|
| редьюсер | своё состояние и как оно меняется | акторов, действия, UI |
| актор | домен и то, что он пушит | UI, маршруты, скоупы |
| фича | свой редьюсер, свой актор, сервисы | UI, какой сегмент её поставил |
| страница / layout | фичу через `cx.state`, свой тулкит | внутренности фичи |

Всё, что выше фичи, — своё у каждого адаптера. Всё, что от фичи и ниже, —
агностично и живёт в ядре приложения.

## Редьюсер

Состояние в центре, `Reducer` реализуется на нём же.

```rust
#[derive(Clone, Debug, Default)]
pub struct Processes {
    pub items: Vec<ProcessRow>,
}

pub enum Update {
    SetItems(Vec<ProcessRow>),
}

impl Reducer for Processes {
    type Update = Update;

    fn reduce(&mut self, update: Update) {
        match update {
            Update::SetItems(items) => self.items = items,
        }
    }
}
```

Два пункта, оба про состояние. Ни `Actions`, ни `Group`, ни `Port` — редьюсер
не может знать, кто его просит, только что изменилось.

Обычный Rust, без макросов. Пять нынешних (`messages!`, `#[port]`,
`#[reducer]`, `#[dispatch]`, `#[derive(ReducerState)]`) порождают
леса, которых у этой формы нет: `#[port]` становится параметром `push`,
`#[dispatch]` — инертная метка, чей смысл живёт внутри `#[reducer]`, а сам
`#[reducer]` выводит тип, которым пользуются все остальные файлы —
`ProcessesReducer`, — сменой регистра у имени функции. Центральная сущность
фичи не встречается в её собственном объявлении.

**Одно правило из этого опыта остаётся: объявление вводит только те имена,
которые в нём написаны.**

## Актор и действия

Действия — это API домена, и принадлежат они актору, потому что отвечает на
них он.

```rust
pub struct Kill(pub u32);
pub struct Refresh;

impl Handler<Kill>    for ProcessActor { … }
impl Handler<Refresh> for ProcessActor { … }
```

Актор принимает действия и пушит `Update`. Синхронно не возвращается ничего:

> Обратно приходит только `Update` в редьюсер.

Ни колбэков, ни футур, ни ответов — UI-поток не может ждать актора, поэтому
запроса с ответом не существует. Следствие, которое стоит держать в голове:
**всё, что нужно UI, обязано быть состоянием.** «Посчитай мне это по запросу»
не бывает; если ответ нужен, он становится полем и приезжает обновлением.

Этот же инвариант — причина, по которой работает снос: нет ни одного пути, где
кто-то ждёт ответа от уже снесённого.

## Фича

Фича — именованная единица со своим временем жизни и одним битом «здесь
установлена». Она соединяет две половины и объявляет, что публикует.

```rust
pub struct ProcessesFeature {
    processes: Bound<Processes>,
}

impl Feature for ProcessesFeature {
    type Exports = Processes;

    fn install(cx: &FeatureCx<Self>, p: &ContextParams) -> anyhow::Result<Self> {
        let processes = cx.state::<Processes>()
            .driven_by(|push| ProcessActor::new(p.context.clone(), push, cx.bus()))?;

        processes.emit(Refresh);
        Ok(Self { processes })
    }
}
```

`Exports` — это `pub` для редьюсеров: перечислен значит доступен другим
сегментам, не перечислен — частный. Внутренние редьюсеры не объявляются вовсе:
заявка и использование в одном месте, ошибиться негде.

`driven_by` — вся проводка целиком. Актор создаётся тем же выражением, что
заявляет редьюсер, поэтому пара известна по построению, а замыкание получает
`push` **параметром** — направление названо там, где им пользуются, а не в
названии метода, который его добывает.

Оттуда же уходит машинерия групп. Сегодня группа действий — это
`HashMap<TypeId, Box<dyn Any>>`, заполняемый отдельным вызовом `wire`;
`InGroup<G>` доказывает лишь членство в объявленном списке, а отправка
незаведённому члену **предупреждает вместо паники**. Всё это существует
потому, что два конца одного ребра заводятся в разных местах. При `driven_by`
доказательством становится `Handler<M>` — актор доказуемо принимает это
действие, — и карте, конус-списку и предупреждению делать больше нечего.

## Сегмент объявляет, что ставит

Список не приписан рядом с телом — он и есть обязательство тела.

```rust
impl Layout for TabsLayout {
    type Installs = (Tabs, Option<AdvancedMetrics>);

    fn init(cx: &Cx<Self>, p: &Params) -> anyhow::Result<Self::Installs> {
        let tabs = cx.install::<Tabs>(p)?;

        let metrics = cx.require::<Settings>()?.advanced
            .then(|| cx.install::<AdvancedMetrics>(p))
            .transpose()?;

        if let Some(m) = &metrics {
            m.follow(tabs.selection());
        }

        Ok((tabs, metrics))
    }
}
```

`cx.install::<T>()` возвращает саму фичу, поэтому тупль собирается из значений,
которые тело действительно произвело. Дрифт не ловится — он невозможен: убрал
строку, и возвращаемый тип перестал сходиться; добавил фичу, и её некуда
положить. `Option<T>` — условная установка, и она же объявляет потребителям,
что отсутствие надо обработать.

Возвращаемые значения — не доказательства ради доказательств: сегмент,
ставящий две фичи, обычно должен их сшить, ради этого они и нужны.

## Доступ к состоянию

```rust
let (state, dispatch) = cx.state::<Processes>();

state.items;
dispatch.emit(Kill(pid));
```

Пара — потому что ролей две, и одно имя их не покрывает. Любая попытка слить их
в одно (`get`, `send`, `ask`, хендл с двумя методами) прячет одну за другой; в
разобранном виде каждая половина называет себя на месте вызова.

`emit` принимает действие значением, поэтому происходящее видно там, где оно
происходит. Порождать метод на каждое действие (`dispatch.kill(pid)`) — значит
завести второе имя тому же самому, выведенное из варианта строкой выше.

Читающая половина — `Rc<R>`, снимок без копии. Ячейка в скоупе держит `Rc<R>`,
и прочесть её значит увеличить счётчик: immediate-режиму это по карману каждый
кадр. Изменение идёт через `Rc::make_mut` — пока снимок никто не держит, оно
правит на месте, а если держат (кадр ещё рисуется, а `emit` уже вызвал
обработчик), правка уходит в копию, и прочитанное остаётся как было. Ради этого
`Reducer` требует `Clone`.

Отличается только то, когда адаптер читает: immediate-режим — каждый кадр,
retained — по подписке, мемоизация — сравнивая снимки по равенству.

## Резолв

`cx.state::<R>()` находит ближайший скоуп, чья фича экспортирует `R`. Поскольку
`routes!` знает предков каждого листа на этапе компиляции, сегмент объявляет
`Installs`, а фича — `Exports`, этот обход сводится к константному индексу
вместо нынешнего перебора, а промах становится ошибкой сборки:

```
error: ни одна фича среди предков `ProcessesPage` не экспортирует `Selection`
       `TabsLayout` ставит `Tabs`, который экспортирует: Processes

error: `MetricsReducer` доступен только условно
       `TabsLayout` ставит `AdvancedMetrics` как `Option<_>` — нужен `try_state`
```

Опциональность распространяется сама: `Maybe` где угодно между использованием и
владельцем делает результат необязательным. Ветка, объявленная в одном месте,
доносится до всех, кого касается, и никто не пишет «для потребителей это
необязательно» руками.

## Состояние приложения и шорткаты плагинов

Приложение тоже владеет состоянием: фича приложения или плагин заявляет `R` и
экспортирует его, а `R` помечен `AppExport`:

```rust
let language = app.state::<Language<L10n>>().seed(initial).plain();
app.export::<Language<L10n>>()?;
```

Тогда `R` читает любой сегмент любого окна, с индексом `FromApp`:
`cx.read::<Language<L10n>, FromApp>()`. Экспорт того, что никто не заявил, —
ошибка, а не тихий `Default`.

Читают через `Reads` — один трейт для страницы и layout'а на WinUI, eframe,
iced и ratatui:

- `read::<R, I>()` — снимок и `Dispatch`; сегмент перерисуется, когда `R`
  изменится (подпиской или потому, что рисует каждый кадр);
- `dispatch::<R, I>()` — только `Dispatch`, без чтения: кнопка, которая
  переключает язык, не перерисовывается от того, что язык переключился.

Slint под `Reads` не подпадает: он собирает вид один раз и связывает его, и
чтение без связи нарисовало бы значение однажды. Там `binding` и `bind`.

Код вне сегмента — фича, плагин, актор при установке — читает через свой
контекст: `cx.read::<R>()` — `Option<Rc<R>>` из этого скоупа или ближайшего
выше, кто `R` экспортирует. Один раз: изменения слышит `observe`.

Плагин, у которого есть что читать, даёт шорткат, а не заставляет писать
`read::<Language<L10n>, FromApp>().0.strings()` у каждого вызова. Соглашение:

- трейт называется `<Плагин>Access`: `L10nAccess`, `StoreAccess`;
- он реализован для любого `C: Reads` (или `C: Services` — для того, что
  плагин даёт сервисом), один раз на все бэкенды;
- методы названы по тому, что возвращают: `cx.l10n::<L10n>()`,
  `cx.settings::<S>()`, — без `get_`, `use_` и `read_`.

```rust
pub trait L10nAccess {
    fn l10n<S: Localization>(&mut self) -> Rc<Language<S>>;
}

impl<C: Reads> L10nAccess for C {
    fn l10n<S: Localization>(&mut self) -> Rc<Language<S>> {
        self.read::<Language<S>, FromApp>().0
    }
}
```

## Как от всего этого отказаться

Каждое объявление выше необязательно. `#[page]` дописывает то, чего автор не
написал — у ассоциированных типов на стабильном Rust нет умолчаний, — и сегмент,
не объявивший ничего, получает `Loose`:

```rust
#[page]
impl Page for Scratch {
    fn init(cx: &Cx<Self>, p: &Params) -> anyhow::Result<()> {
        let actor = cx.spawn(WhateverActor::new(cx.push::<Whatever>()));
        actor.send(Go);
        Ok(())
    }
}
```

Цепочка, где встретился `Loose`, резолвит `cx.state::<R>()` в рантайме, с
сегодняшней паникой при промахе. Гарантия деградирует ровно в том звене, где нет
знания, и не дальше: строгий layout над ленивой страницей свои проверки
сохраняет.

**Место вызова между режимами не меняется.** Никакого `state_dyn` для ленивого
пути — иначе переход от свободного к строгому потребовал бы правки всех
потребителей, то есть никто бы его не сделал.

Больше не деградирует ничто. Снос, разделы ячеек, типизированные параметры,
гварды и `~` — свойства устройства, а не объявлений. Строгий режим ничего не
включает, он только запрещает ошибаться, и это правильная сторона для
необязательного.

## Несколько экземпляров одной фичи

Два списка в одном скоупе — это две фичи, и различаются они типом-маркером, а не
строкой:

```rust
cx.install::<ListFeature<Recent>>(p)?;
cx.install::<ListFeature<Archived>>(p)?;
```

Это единственное место, где все просмотренные DI отрастили строковый запасной
выход — `@Qualifier`, `named()`, `instanceName`, — и где ответ Riverpod лучше:
ключом должен быть символ, который компилятор и так отслеживает.

Их продукты столкнулись бы в скоупе, ключуемом типом редьюсера, поэтому скоуп
перестаёт быть плоской картой и становится набором разделов по экземплярам фич.
Это и есть «фича — единица», доведённое до уровня хранения; заодно исчезает
нынешний реестр `installed_features`, в единственном `HashSet` которого лежат
ключи двух разных сортов: `TypeId` install-замыкания (уникальность через
`assert`) и `TypeId` редьюсера (идемпотентно).

## Что это заменяет

Нынешний `FeatureInitContext` даёт четыре способа заявить редьюсер — `port`,
`actions`, `wire`, `seed_reducer`, — и владение оказывается побочным эффектом
того, какой из них позвали. Здесь способ один: `cx.state::<R>()`, с
необязательными продолжениями `.seed(..)` и `.driven_by(..)`. Чистое состояние
вида без актора перестаёт выглядеть недоделанной фичей — это редьюсер без
`driven_by`.

Уровень фичи как единицы в коде уже есть и полностью мёртв:
`FeatureInitContext::install` и `inherit` не вызываются нигде, а
`mark_feature_installed` зовётся только из `install`. На практике
`installed_features` содержит только идентификаторы редьюсеров, а `inherit` —
утверждение, которое ничего не возвращает; недостающая половина в том, что оно
должно возвращать фичу.

Два доккомментария до сих пор ссылаются на `resolve_owner` — функцию, которой в
дереве нет.

## Открытое

- Где носить тип актора, чтобы `emit` проверялся через `Handler<M>`, а UI при
  этом актора не называл. Очевидный ответ — `Reducer::DrivenBy`, ценой того, что
  домен упоминает собственного актора; возможно, это приемлемо.
- Снос идёт снаружи внутрь: `Vec::truncate` роняет элементы с начала, поэтому
  акторы layout'а утилизируются раньше акторов страницы под ним. Чинить
  направление стоит после того, как объявлены зависимости: страница, сказавшая,
  что читает состояние layout'а, — это и есть то, что делает «layout обязан её
  пережить» фактом, а не догадкой.
- Становится ли `Exports` таким же обязательством возврата `install`, каким стал
  `Installs`.
