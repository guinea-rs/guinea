# Регионы: слоты, части и проверка достижимости там, где читают

**Статус: в работе.** Сделано: достижимость при чтении (`decf1e3`), проверка
построения без слотов (`c7678a5`), слоты с заполнением от активного ребёнка
на WinUI (`82e48a9`), части. `child_routes` и `each_route` — впереди. Слоты на eframe,
iced, ratatui и Slint не сделаны: там layout рисуется в том же проходе, что
и ребёнок, и плейсхолдер устроен иначе — отдельное решение, когда
понадобится.
Критерий приёмки — `ShellLayout` из uniproc, переписанный в конце документа.

## Тезис

`Installs` и `Exports` остаются как есть. Только они знают, что где
установлено и с какого момента: `Installs` сегмента — это значение, которое
возвращает его `install`, а `Exports` сверяется с тем, что фича на самом деле
заявила, в момент, когда она заканчивает установку.

Уходит другая половина — доказательство при компиляции, что читатель
дотягивается до того, что читает. `Segment::Above`, `Reaches<R, I>` и индекс
`I` существуют ради этого одного доказательства, а оно опирается на
допущение, с которым следующие возможности жить не могут.

Взамен не появляется никакого нового объявления. Что сегмент читает, уже
сказано там, где он читает: `cx.read::<R>()` на контексте, который знает
сегмент. Что достижимо, уже сказано `Installs` и `Exports` вдоль цепочки.
Поиск, который отвечает на это во время работы, есть уже сейчас.

## Почему достижимость при компиляции должна уйти

`type Above` — ассоциированный тип, значит, у каждого типа сегмента ровно одно
место в ровно одном дереве. Код уже обходит это:

- `check_layouts` отказывает layout'у, который в двух местах стоит под разными
  layout'ами;
- страница, названная в `routes!` дважды, получает два `impl Segment` и не
  компилируется;
- `Layout::Params` — пересечение по всем местам, где layout встречается,
  потому что у типа может быть только один ответ.

Layout, который рисует что-то кроме своего outlet, ломает это окончательно.
Что показывает слот, зависит от того, какой ребёнок активен во время работы,
поэтому статического типа у содержимого нет. А доказательство на уровне
типов, кто какой слот может заполнять, потребовало бы ещё одного cons-списка
поверх `Above`.

Сколько доказательство стоит сейчас: `_` в каждом `read::<R, _>()`,
`Above`-списки в каждой сгенерированной `impl Segment`, токены
`Installed<T>`, длинные `on_unimplemented`, одно место на тип. Даёт оно одну
ошибку компиляции, которая превращается в панику на первом рендере
сегмента, читающего неправильно.

## Что остаётся, что уходит

| | |
|---|---|
| остаётся | `Installs`, `Exports`, `#[installs]`, `app!` как единственное место, где объявлено приложение, `routes!` как единственное место, где объявлена структура окна, поиск во время работы через `Scope::owner_of` |
| уходит | `Segment::Above`, `Reaches`, индекс `I`, правило «одно место» из `check_layouts` |
| новое | маркеры `#[slot]`, `part(..) => Slot` в `routes!`, `cx.slot`, `cx.fill`, `cx.child_routes`, `Mounted::each_route` |

`Installed<T>` существовал, чтобы у приложения был статический `Installs` для
`Reaches`. Выживет ли он — открытый вопрос ниже.

## Построение проверяется до любого монтажа

Из чего состоит дерево, известно без рендера: форма, которую объявил
`routes!`, `Installs` каждого сегмента и через них все `Exports`. Первая
навигация роутера проверяет всё это по всем веткам дерева, к которому
относится маршрут, раньше, чем что-нибудь установит. Не `Router::new`: роутер
создаётся без дерева и узнаёт `Route` только из навигации.

Чтобы это прочесть, `Installs` должен уметь перечислить себя: он ограничен
трейтом `Lists`, который есть у фичи, `Bound<R>`, `Option<_>` и кортежей.
`SegmentEntry` несёт этот список, `RouteChain::tree()` отдаёт все цепочки, а
`construction::check` их обходит. Проверяется:

- фича, поставленная дважды на одной цепочке: layout поставил, и страница под
  ним поставила снова, или один сегмент перечислил её дважды;
- две части, объявленные в один слот одного layout'а (вместе со слотами);
- дерево растёт из `app(App)`, а `App` не установлен — паника, как и сейчас;
- reducer, который экспортируют два сегмента на одной цепочке, и ближний
  молча скрывает дальний. Это предупреждение, а не отказ: скрытие может быть
  задумано.

Находка называет сегменты, которые её вызвали, а не маршрут, поэтому общий
префикс нескольких маршрутов даёт одну строку:

```
the route tree is built wrong:
  `Chrome` is installed by `Shell`, and again by `Doubling` below it
```

Что приложение экспортирует, проверка пока не видит: `App` ставится до
роутера, и его экспорты известны только рантайм-скоупу.

Что сегмент читает и чем заполняет слоты, к построению не относится: это
сказано во `view`, и до запуска `view` этого никто не знает. Эта половина
проверяется там, где сказана.

## Достижимость проверяется там, где читают

`cx.read::<R>()` теряет `_`, больше для читателя ничего не меняется:

```rust
fn view(&self, cx: &mut PageCx<'_, '_, Self>) -> View {
    let (state, dispatch) = cx.read::<ProcessesState>();
    let (settings, _) = cx.read::<SettingsState>();
    ...
}
```

Чтение, которое ни до чего не дотягивается, паникует на том рендере, который
его делает, и говорит, что прошло:

```
`SidebarCharts` reads `SettingsState`, but nothing reaches it:
  SidebarCharts (part of Shell) <- Shell <- MainWindow <- application App
  `SettingsState` is exported by `SettingsFeature`, which nothing here installs
```

Цена — в том, когда это видно: на первом рендере сегмента, а не при
компиляции. Страницу, которую не монтирует ни один тест, первым смонтирует
пользователь. Это закрывает одна строка в тестах приложения, без списков на
сегментах:

```rust
#[guinea::test]
fn every_route_renders(h: &mut Harness) {
    start(h);
    Mounted::each_route::<Route>(h).unwrap();
}
```

`each_route` монтирует каждый маршрут, объявленный в `routes!`, вместе с его
частями, рендерит один раз, дожидается, пока всё уляжется, и сообщает все
неудачные чтения, заполнения и слоты разом. Чтение в ветке, в которую первый
рендер не заходит, не покрыто — как и сейчас ничем, кроме компилятора.

## Окно — это верхний layout

Нового понятия нет. Всё, что относится к окну, — визуальные настройки, тема,
цветовая схема, которую получает всё ниже, память маршрута — живёт в layout'е
в корне дерева. Договорённости хватит, пока не покажут, что её мало.

## Слоты

Слот — это маркерный тип:

```rust
#[slot]
pub struct Toolbar;

#[slot]
pub struct PaneFooter;
```

Layout размещает его в своём view так же, как outlet. Разместить — и значит
объявить; списка на layout'е нет:

```rust
NavigationView::new()
    .header(cx.slot::<Toolbar>())
    .pane_footer(cx.slot::<PaneFooter>())
    .content(cx.outlet())
```

Слот заполняется с двух сторон.

**Частью (part)** — она объявлена в `routes!` и монтируется вместе со своим
layout'ом:

```rust
layout(Shell) {
    part(SidebarCharts) => PaneFooter
    page(Services)
}
```

Часть — это `Page`: свои `Installs`, `Message` и состояние. У неё нет варианта
в `Route`, её `Params` — `()`, и живёт она ровно столько, сколько её layout, —
засыпает, когда засыпает `keep`-layout. Один и тот же тип может быть частью
нескольких layout'ов: ничто больше не привязывает его к одному месту. Две
части в одном слоте одного layout'а — ошибка `routes!`.

Скоуп части — ребёнок скоупа layout'а в outlet'е с именем слота, поэтому
часть читает то, что читает её layout, и уходит вместе с ним. Её цепочка —
layout'ы до её layout'а и она сама: так её видит и проверка построения, и
сообщение о недостижимом чтении.

Пока слот заполнен снизу, компонент части размонтирован (у реактора нет
`Visibility`, чтобы её просто спрятать), но её узел живёт в её скоупе:
узел страницы теперь хранится по скоупу, а не забирается один раз, и
вернувшаяся часть показывает то же состояние.

**Активным ребёнком.** Любой сегмент на активной цепочке под layout'ом
заполняет слот из своего view:

```rust
fn view(&self, cx: &mut PageCx<'_, '_, Self>) -> View {
    let (state, dispatch) = cx.read::<ProcessesState>();
    cx.fill::<Toolbar>(toolbar(&state, &dispatch));
    table(&state, &dispatch)
}
```

Побеждает самое внутреннее заполнение на активной цепочке; часть — это то,
что слот показывает, когда снизу его никто не заполняет. Колбеки внутри
заполнения принадлежат сегменту, который заполнил, поэтому кнопка тулбара в
`Shell` действует на `Processes`.

Две ошибки видны только после рендера layout'а, и обе тогда паникуют в debug:
часть, чей слот layout так и не разместил, и заполнение слота, который никто
выше не разместил.

### Как заполнение доходит до слота

Layout рендерится раньше ребёнка, поэтому не может дождаться его заполнения.
`cx.slot::<S>()` размещает свой маленький компонент. Заполнение передаётся
этому компоненту после того, как рендер ребёнка зафиксирован, и
перерисовывается только он — не layout и не outlet под ним.

Следствия, все намеренные:

- заполнение появляется через один drain после рендера ребёнка, никогда в том
  же;
- заполнение, равное прошлому (`View: PartialEq`), не доставляется;
- уход с сегмента или засыпание `keep`-layout'а снимает его заполнения в том
  же drain, в котором приходят заполнения следующего сегмента, так что
  навигация не мигает пустым тулбаром.

## Навигация из дерева

`cx.child_routes::<Route>()` отдаёт layout'у его детей: `Route` каждого и
признак, текущий ли он. Подписи и иконки берутся из исчерпывающего `match` по
`Route` во view, так что страница, добавленная в `routes!` и забытая в меню, —
ошибка компиляции, а не строковый тег, который никто не сопоставил.

## Что и когда ловится

| ошибка | когда ловится |
|---|---|
| фича поставлена дважды на одной цепочке | сборка роутера |
| две части в одном слоте одного layout'а | сборка роутера |
| reducer экспортирован дважды на одной цепочке | сборка роутера, предупреждение |
| чтение reducer'а, до которого ничего не дотягивается | рендер, который читает; `each_route` в тестах |
| часть, чей слот layout не размещает | первый рендер layout'а, debug; `each_route` |
| заполнение слота, который никто выше не размещает | рендер, который заполняет, debug; `each_route` |
| дочерний маршрут забыт в меню | компиляция, исчерпывающий `match` |
| экспорт reducer'а, который фича не заявила | конец `install`, как сейчас |

## Пример для приёмки

Оболочка uniproc, где всё, что `ShellLayout` знает сейчас, разнесено туда,
где ему место.

```rust
routes! {
    Route {
        app(App) {
            layout(MainWindow) restorable {
                layout(Shell) {
                    part(SidebarCharts) => PaneFooter
                    part(Connecting) => Overlay
                    layout(ProcessesArea) keep {
                        page(Processes)
                        page(ProcessesSettings)
                    }
                    page(Services)
                    page(Wsl)
                    layout(SystemArea) {
                        page(System)
                        page(SystemTools)
                    }
                    page(Settings)
                }
            }
        }
    }
}
```

`SettingsFeature` переезжает в `app!`: настройки читаются по всему дереву, и
то, что их ставил `Shell`, было размещением ради удобства.

```rust
#[layout]
impl Layout for MainWindow {
    type Installs = ();
    type Message = ColorScheme;

    fn view(&self, cx: &mut LayoutCx<'_, '_, Self>) -> View {
        let on_scheme = cx.on(|scheme| scheme);
        cx.on_color_scheme(on_scheme);

        let (settings, _) = cx.read::<SettingsState>();
        cx.window_visuals(WindowVisuals::new().backdrop(WindowBackdrop::Mica).theme(window_theme(settings.theme)));

        provide(scheme_context(), self.scheme, cx.outlet())
    }
}

#[layout]
impl Layout for Shell {
    type Installs = (SidebarFeature,);
    type Message = ShellMsg;

    fn view(&self, cx: &mut LayoutCx<'_, '_, Self>) -> View {
        let (sidebar, _) = cx.read::<SidebarState>();
        let l10n = ui::l10n::use_tr(cx);
        let nav = cx.use_navigate::<Route>();

        ui::shell_view(ui::ShellProps {
            l10n: &l10n,
            menu: cx.child_routes::<Route>(),
            open: sidebar.open,
            width: sidebar.width as f64,
            header: cx.slot::<Toolbar>(),
            footer: cx.slot::<PaneFooter>(),
            overlay: cx.slot::<Overlay>(),
            content: cx.outlet(),
            on_select: Callback::new(move |route: Route| nav.to(route)),
            on_resize: cx.on(ShellMsg::Resize),
            on_open_changed: cx.on(ShellMsg::OpenChanged),
        })
    }
}

#[page]
impl Page for SidebarCharts {
    type Installs = (MetricsFeature,);
    type Message = ();

    fn view(&self, cx: &mut PageCx<'_, '_, Self>) -> View {
        let (metrics, _) = cx.read::<MetricsState>();
        let (settings, dispatch) = cx.read::<SettingsState>();
        ui::sidebar_charts(&metrics, &self.charts, &settings, dispatch)
    }
}
```

`Connecting` устроен так же: ставит `AgentLinkFeature`, читает
`AgentLinkState` и заполняет `Overlay` заставкой или ничем.

Что меняется во время работы: пуш метрик перерисовывает `SidebarCharts` и
больше ничего. `Shell` перерисовывается, когда панель открывают, закрывают
или тянут за край, и страница под ним перерисовывается вместе с ним — хотя
её вход не изменился. Это регрессия реактора в третьем превью (#5000):
ребёнок с равным `Input` рендерится снова. Issue про неё остаётся в силе.

## Открытые вопросы

1. **`Installed<T>`.** Он нужен, чтобы у приложения был статический
   `Installs` для `Reaches`. Без `Reaches` `app!` может остаться единственным
   местом объявления приложения, а `#[installs] fn app` — возвращать `()`.
   Убрать токены или оставить как доказательство, что всё перечисленное в
   `app!` установлено?
2. **Часть с params.** Сейчас `()`; часть, которой нужен маршрут, читает его
   через `use_route`. Если этого не хватит, `part(..)` может получать params
   своего layout'а.
3. **Несколько заполнений на одной цепочке.** Побеждает самое внутреннее.
   Layout, которому нужно их сложить — хлебные крошки, например, — нужен весь
   стек, а не победитель. Второй вид слота сейчас или позже?

## Миграция

Каждый `read::<R, _>()` теряет `_`, компилятор укажет на каждый. Рукописные
`impl Segment` удаляются целиком. Значение в `Installs`, которое не фича и не
`Bound<R>`, получает `impl Lists` с пустым списком. Ниже по зависимостям:
uniproc (его сегменты и `ShellLayout`, разнесённый как выше), guinea-plugins
(страницы devtools, `L10nAccess`), примеры.

Релиз: всё идёт в 0.23, которая ещё не помечена тегом.
